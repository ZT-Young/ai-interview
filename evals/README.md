# evals —— AI 效果评测

这个目录回答一个此前没人能回答的问题：**模型的输出到底好不好、稳不稳**。

`pnpm test` 只能证明「代码没写错」，证明不了「评分评得准」。这里是后者。

## 目录

```
evals/
├── README.md              ← 你在这里
├── cases/scoring-v1.json  ← 评分器评测用例集（简历 + JD + 三档答案）
├── cases/followup-v1.json ← 追问决策用例集（6 例，含 2 个「必须查简历」的难例）
└── reports/               ← 每次运行的原始记录与 latest.md（本地产物）
```

## 怎么跑

```bash
pnpm eval:agent                   # 追问决策：旧链路 vs Agent 对比（约 12 次调用，1 分钟）
pnpm eval:scoring                 # 每档重复 2 次（约 14 次模型调用，3 分钟左右）
pnpm eval:scoring --runs 3        # 一致性结论更可靠
pnpm eval:scoring --only q1-project-depth
```

需要 `LLM_API_KEY / LLM_BASE_URL / LLM_MODEL`（真实调用模型），
**不需要数据库** —— 评测不写任何表，也不写 `ai_call_logs`，避免污染线上质量看板口径。

配套的质量看板（读 `ai_call_logs`，需要数据库）：

```bash
pnpm ai:quality                   # 近 30 天：成功率 / P50-P99 时延 / token 与成本
pnpm ai:quality --days 7 --json .local/ai-quality.json
```

## 测什么

| 指标 | 口径 | 为什么重要 |
|---|---|---|
| **一致性** | 同一份答案重复评分，分数的标准差与极差 | 抖动大 = 分数不可信，用户会觉得"玄学" |
| **区分度** | 好答案 / 中等 / 敷衍 三档是否单调递减，以及极差 | **评分器是否有效**的核心判据：分不开三档，分数就是噪声 |
| **证据合规** | `evidence_quotes` 通过原文子串校验的比例 | 对应 AGENTS.md N6：无证据不给分 |
| **硬约束** | 未作答是否六维全 0、低分是否给了可执行建议 | 对应 N6 / N7 |
| **代价** | 重试率、平均与 P95 时延 | 决定体验与成本，也是容量规划依据 |

## 设计原则：不断言绝对分数

用例集**没有**写「这道题必须给 4 分」。

绝对分数会随模型、prompt、随机性漂移，断言绝对值只会得到一堆反复失效的断言，
逼着人不断去改期望值，最后谁也不信这个评测。
**相对顺序**（好 > 中 > 敷衍）才是稳定的、能反映评分器质量的判据。

同理，断言都落在**可自动判定**的维度上，不需要人工逐条打分 ——
否则评测会因为"没人有空标"而荒废。

## 基线（2026-09-28，模型 deepseek，runs=2）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 成功率 | 85.7%（12/14） | **100%（14/14）** |
| 一致性（平均标准差） | 1.4 分 | 2.2 分 |
| 证据合规 | 42/42 · 100% | 42/42 · 100% |
| 重试率 | 28.6% | **14.3%** |
| 区分度 q1 | 85 / 48.4 / 28.4 · 顺序正确 | 86.7 / 45 / 28.4 · 顺序正确 |
| 区分度 q2 | 88.4 / 45 / 23.3 · 顺序正确 | 90 / 45 / 26.7 · 顺序正确 |

结论：**评分器是有效的** —— 三档答案被稳定区分（极差 58–63 分），
证据引用 100% 来自原文，同一答案重复评分抖动在 2 分左右（百分制）。

已知局限（别拿这组数字吹过头）：

- **样本太小**：2 道题 × 3 档 × 2 次重复。标准差在 2 次样本上不稳定
  （修复后最大 6.6 分就是 poor 档两次差了 13 分造成的）。
  要下"一致性 ±X 分"的结论，至少 `--runs 5`。
- **没有人工标注**：只有相对顺序，没有"人类面试官会打几分"的对齐数据。
- **只覆盖评分**：出题、追问、报告生成还没进评测集。

## 已知缺陷（由本评测发现）

### 空回答的评分 100% 失败（已修复）

`evidence_quotes` 的 schema 强制 `min(1)`，但**未作答时不存在任何可引用的原文**，
于是模型只能编造引用或被判为格式错误 → 两次重试后返回 `evaluation_failed`。
用户在面试中跳过某题，这道题就永远评不了分。

修法（把业务规则从 schema 上移到服务层）：

1. schema 去掉 `min(1)` —— 结构层只管形状，"非空回答必须有证据"是业务规则
2. 新增 `applyNoAnswerRule()`（`lib/ai/schemas/evaluation.ts`，纯函数、有单测）：
   未作答时服务端强制六维归零 + 清空证据 + 补说明文案，**不信任模型给的同情分**
3. prompt 规则 1 明确写出例外：未作答时 `evidence_quotes` 必须为空数组

修复后该用例从「2/2 失败」变为「2/2 给 0 分」，整体重试率从 28.6% 降到 14.3%。

## 追问决策评测（eval:agent）

`pnpm eval:agent` 对**同一批用例**跑两种策略：

- `legacy`：旧的单次调用链路（`buildFollowUpPrompt` + schema + 后置校验）
- `agent`：新的面试官 Agent（可先检索简历 / JD / 历史 / 已问题目，再决策）

期望值只判**决策方向**（追问 / 下一题 + 原因类别），不判措辞。
另有一个参考指标「追问锚定率」：追问是否指向简历里真实存在的细节
（关键词硬匹配，会漏同义表达，**只作参考**，追问原文会一并落盘供人工核查）。

为什么要做这个对比：「加了 agent」本身不是成绩，谁都能把一次调用改成循环。
能回答「变好在哪、贵了多少」才算数。基线数字见
[docs/engineering/AI_QUALITY_BASELINE.md](./../docs/engineering/AI_QUALITY_BASELINE.md) §3.5。
