## 1. 优先级总览

证据强度定义：
- **强** = 有明确事实支撑（代码现状 / 合规硬要求 / 阻塞项）
- **中** = 有间接依据（工程惯例 / 相邻功能缺失）
- **弱** = 属推测，**必须等内测数据**才能排进计划

| 优先级 | 事项 | 证据强度 | 为什么现在做 | 验证方式 |
|---|---|---|---|---|
| **P0** | 埋点落地 + 漏斗看板 | **强** | 不埋点就没有任何数据，后续所有决策都是猜 | 事件实际产生、SQL 可复现指标 |
| **P0** | 接入真实支付渠道 | **强** | 付费率恒为 0，**变现闭环未真正闭环** | 真实成单、`payment_succeeded` 有记录 |
| **P0** | `git init` + CI 生效 | **强** | 无版本控制已多次导致文件被覆盖后靠记忆重建；CI 已配置但仓库无 git 时密钥检查是空转 | 远端仓库存在、CI 实际跑过 |
| **P1** | 补真实数据库凭证，跑通 152 个集成测试 | **强** | 31% 的测试在空转，**已上线代码从未被真实验证过** | `pnpm test` 0 跳过 |
| **P1** | 接入 ASR（语音面试） | **强** | 功能标称已提供但实际返回「暂不可用」，属**承诺未兑现** | 真实录音可转写 |
| **P1** | 隐私政策版本提升（因新增行为采集） | **强** | 埋点属处理目的变更，**合规硬要求**，与 P0 埋点同批上线 | 政策含行为采集说明且版本号已升 |
| **P2** | 内测问卷投放与回收 | **强** | 是 H1–H5 假设的唯一验证手段 | 回收 ≥ 30 份有效问卷 |
| **P2** | `docs/TASKS.md` 补齐 | 中 | 工程可维护性；当前任务拆解只存在于对话中 | 文档可指导新成员接手 |
| **P3** | 追问质量 / 报告可信度优化 | **弱** | **方向正确但无法确认哪一项最痛** | 必须等问卷第 10–11、17–18 题结果 |
| **P3** | 免费额度规则调整 | **弱** | 当前 1 次是否合适未知 | 等激活率与问卷第 22 题结果 |
| **P3** | 报告页「回答要点提示」增强 | **弱** | 取决于问卷第 19 题 | 等数据 |

> **P0 三项的共同点**：都不是「做功能」，而是**让产品能被真实测量与验证**。
> 在内测前必须先解决，否则内测本身也拿不到有效结论。

## 2. 第一批（内测前必须完成）

### 2.1 埋点落地 + 隐私政策同步

**做什么**（设计见 [METRICS.md](./METRICS.md)）：
1. `analytics_events` 表与迁移
2. 五个事件的触发点接入；**`payment_succeeded` 仅服务端可写**
3. `pay_checkout_clicked` 前端上报接口（服务端校验 `user_id` 来自会话）
4. **同步更新隐私政策**：说明「会采集哪些行为数据、用于什么、如何删除」，`LEGAL_VERSION` → v2
5. 用户删号时 `analytics_events` 按 `user_id` 匿名化

**为什么两条必须同批上线**：先埋点后补政策 = 未经同意采集数据（AGENTS.md §7 C1）。
**验收**：`pnpm test` 含「事件不含 PII」与「仅服务端可写 `payment_succeeded`」断言。

### 2.2 接入真实支付渠道

**做什么**：
1. 确认渠道（微信 / 支付宝 / Stripe）与解锁模型（单份 / 次数包 / 订阅）
2. 替换 `lib/payments/provider.ts` 的签名与报文解析
3. 配置 `PAYMENT_WEBHOOK_SECRET`；回调路由的业务逻辑**无需改动**（验签 → 幂等 → 发放已就绪）

**风险与前置**：
- 回调需要**公网可达地址**（Vercel 域名可用）
- 微信/支付宝需企业资质，**个人主体可能无法接入** —— 若内测阶段只有个人主体，
  建议先接 Stripe 或继续用兑换码，并把「付费率」指标标注为「不可测」

**验收**：真实支付一笔，`payment_succeeded` 有记录、权益正确发放、重复回调不重复发放。

### 2.3 `git init` 与 CI 生效

**做什么**：初始化仓库 → 推送到远端 → 确认 CI 四步与密钥检查实际跑过。

**为什么是 P0**：`.github/workflows/ci.yml` 与 `scripts/check-secrets.mjs` **都已写好但从未执行过**；
没有 git 仓库时「检查 `.env` 是否被跟踪」这一步直接跳过。

## 4. 第三批（内测后按数据决定）

**这一批的排序完全依赖问卷与埋点数据，此处只列出候选与判断依据，不做承诺。**

| 候选 | 触发条件（若数据表明…则做） | 数据来源 |
|---|---|---|
| 提升解析准确率 / 降低确认负担 | 问卷第 5–7 题偏低，或第 13–14 题中「要手工改」提及率高 | 问卷 5–7、13–14 |
| 调整追问策略（层数或提问方式） | 第 10–11 题偏低，或 METRICS 的「追问被采纳率」异常 | 问卷 10–11、`ai_call_logs` |
| 优化报告结构 | 第 15–17 题偏低，或「报告打开率」显著低于「完面率」 | 问卷 15–17、METRICS §3.2 |
| 调整定价或免费额度 | 第 22 题的价格分布与当前定价差距大；或付费率有数据但偏低 | 问卷 22–23、METRICS §3.3 |
| 语音面试优先化 | 第 20 题多数选「语音」 | 问卷 20–21 |
| 性能优化（长页/生成耗时） | 第 13 题「等待太久」提及率高，或 P95 耗时超预期 | 问卷 13–14、`ai_call_logs.duration_ms` |

**明确不做**（除非用户强烈要求且通过合规评估）：
- ❌ 生成可直接背诵的「标准答案逐字稿」—— 会诱发编造经历（AGENTS.md §6.1 N4）
- ❌ 语速/停顿/声纹类「表达特征」分析 —— 触及 §3.2 非目标
- ❌ 自动淘汰、录用建议类输出 —— 违反 §7 C5
