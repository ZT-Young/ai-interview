# AI 质量基线与评测

本文件是**效果侧的唯一真源**：模型的稳定性、速度、成本与评分质量基线放在这里，
每次改 prompt / 换模型 / 调 schema 之后重跑并更新。

- 质量看板：`pnpm ai:quality`（读 `ai_call_logs`）
- 评分评测：`pnpm eval:scoring`（真实调模型，见 [../../evals/README.md](../../evals/README.md)）

## 1. 为什么需要这个

此前的状态是：`ai_call_logs` 一直在记录调用数据，但**没有任何东西去读它**；
评分准不准更是全靠体感。结果是「功能做完了，但说不清做得好不好」——
改 prompt 之后不知道是变好还是变差，只能凭印象。

## 2. 运行质量基线

采集时间 2026-09-28，覆盖全部历史（`--days 3650`），单价按 输入 ¥2 / 输出 ¥8 每百万 token 估算。

| 指标 | 值 |
|---|---|
| 总调用 | 203 次 |
| 成功率 | 81.8%（166 成功 / 37 失败） |
| token | 输入 128,618 / 输出 141,179 |
| 估算总成本 | ¥1.39（单次 ¥0.0068） |

按操作拆分：

| operation | 调用 | 成功率 | P50 | P95 | P99 | 输出 token |
|---|---|---|---|---|---|---|
| hint | 57 | 65% | 1093ms | 2045ms | 3154ms | 5,664 |
| parse_resume | 54 | 83% | 1824ms | 12665ms | 35744ms | 29,111 |
| parse_jd | 53 | 87% | 1263ms | 2768ms | 5043ms | 11,731 |
| plan | 12 | 100% | 19748ms | 27735ms | 29316ms | 55,952 |
| match | 10 | 100% | 6133ms | 16752ms | 18276ms | 17,458 |
| evaluate | 7 | 100% | 10239ms | 12195ms | 12453ms | 13,526 |
| follow_up | 7 | 86% | 1927ms | 2820ms | 2889ms | 1,933 |
| report | 3 | 100% | 7887ms | 13035ms | 13493ms | 5,804 |

失败原因分布：`missing_env` 35 次、`provider_error` 1 次、`timeout` 1 次。

**读这份数据时的三个判断：**

1. **35 次 `missing_env` 是配置期的历史噪音**，不是真实故障 —— 剔除后真实成功率约 99%。
   这说明看板必须按错误码下钻，只看总成功率会得出错误结论。
2. **plan 的 P50 接近 20 秒**，是全流程最慢的一环（一次生成 8–12 道题 + 输出 token 最多）。
   这是体感卡顿的主要来源，优化优先级最高。
3. **hint 成功率仅 65%**，而 parse_* 都在 83% 以上 —— hint 是短输出场景，
   失败原因待下钻（看板目前只给了错误码，需要结合 `/admin/logs` 看具体 violation）。

## 3. 评分质量基线

用例集 `evals/cases/scoring-v1.json`（2 题 × 好/中/敷衍三档 + 1 个空回答），每档重复 2 次。

| 指标 | 结果 |
|---|---|
| 成功率 | 100%（14/14） |
| 一致性 | 平均标准差 2.2 分（百分制），最大 6.6 分 |
| 证据合规 | 42/42 条引用通过原文子串校验，100% |
| 重试率 | 14.3% |
| 区分度 | q1：86.7 / 45 / 28.4（顺序正确，极差 58.3）<br>q2：90 / 45 / 26.7（顺序正确，极差 63.3） |
| 时延 | 平均 10.1s，P95 12.5s |

**结论**：评分器有效 —— 三档答案被稳定区分（极差 58–63 分），
证据 100% 来自原文，重复评分抖动约 2 分。

**局限**（不要拿这组数字下强结论）：2 道题、每档仅 2 次重复，
标准差在小样本上不稳定；没有人工标注做绝对对齐；只覆盖评分，未覆盖出题与报告。

## 3.5 Agent 化对比（追问决策）

用例集 `evals/cases/followup-v1.json`，6 个用例（含 2 个「必须查简历才能问好」的难例），
同一批用例分别跑**旧链路**（单次调用）与**Agent**（检索后决策）：

```bash
pnpm eval:agent            # 两种策略对比
pnpm eval:agent --only agent
```

| 策略 | 决策准确率 | 失败率 | 证据合规 | 单问合规 | 平均工具调用 | 平均时延 |
|---|---|---|---|---|---|---|
| legacy（单次调用） | 83.3% | 0% | 100% | 83.3% | 0 | 1703ms |
| **agent（检索后决策）** | **100%** | 0% | 83.3% | **100%** | 1.7 | 6099ms |

**结论（要连同代价一起讲）**：

- Agent 把决策准确率从 83.3% 提到 100%，且**不再出现「一题多问」**；
  典型的 legacy 失效场景是「回答已经很充分，却仍然追问」。
- 代价是**时延约 3.6 倍**（1.7s → 6.1s）：每轮检索都是一次完整模型调用。
  追问发生在用户答完之后，6 秒仍在可接受范围，但这是实打实的成本，不是免费的。
- 工具不是每次都用：模型在「回答明显充分、直接进下一题」的场景会跳过检索
  （评测中 f2 用了 0 次工具），说明 prompt 里「只判断方向时别查」的约束生效了。
- 证据合规 agent 83.3% 略低于 legacy 100%：有一条 `focus` 不是回答原文的子串。
  值得作为下一轮 prompt 优化的目标。

**别过度解读**：用例只有 6 条、每组 1 次，准确率差异在统计上不显著。
能下的结论是「Agent 在难例上表现更好且没有退化」，不是「Agent 一定强 X%」。

后续优化方向：同轮多工具并行、对「明确进入下一题」的场景提前短路、
工具结果按会话缓存（同一场面试里简历是固定的）。

## 4. 评测发现的缺陷

### 4.1 空回答评分 100% 失败（已修复）

`evidence_quotes` schema 强制 `min(1)`，但未作答时不存在可引用的原文 → 必然失败。
修复：schema 去掉 `min(1)`，新增服务层纯函数 `applyNoAnswerRule()` 强制归零兜底。
修前成功率 85.7%，修后 100%；重试率 28.6% → 14.3%。详见 evals/README.md。

### 4.2 `prompt_version` 从未落库（已修复）

**根因不是"忘了传"**：`LlmRequest` 接口压根没有 `promptVersion` 字段，
唯一的 `logAiSuccess()` 调用点（`lib/parsing/llm-port.ts`）无从取值，
所以看板里该字段恒为 `unknown`。

后果：**无法按 prompt 版本做 A/B 对比**。改了 prompt 之后，
看板上成功率和时延的变化无法归因到"是哪一版 prompt"，只能凭记忆。

**已修**（`tests/unit/prompt-version.test.ts` 8 例守卫）：

- `LlmRequest` 与 `parseWithRetry` 的 `AttemptInput` 增加 `promptVersion`，端口层透传
- 各 prompt 模块导出自己的 `PROMPT_VERSION`，形如 `parse.jd@1` / `plan@1` /
  `evaluation@1` / `report@1` / `followUp@1` / `hint@1` / `interviewAgent@1`
- 8 个调用点全部传入自己那个 prompt 的版本；测试断言版本值全局唯一、非空、带 `@n` 后缀

**纪律**：改 prompt 的措辞、规则或输出结构时，必须递增对应版本号（`@1` → `@2`）。
不递增的话，这次改动会被记到旧版本名下，归因直接失效。
注意 `evaluations.prompt_version` 写的是 `SCHEMA_VERSION`（契约版本），
与 `ai_call_logs.prompt_version`（prompt 版本）是两回事，不要混用。

## 5. 更新纪律

- 改 prompt / 模型 / schema 后**必须**重跑 `pnpm eval:scoring`，把新数字追加到本文件并注明变化原因
- 看板数字每月或每次发版前刷新一次（`pnpm ai:quality --json` 留档）
- 基线退化（成功率下降、区分度不成立、证据合规跌破 95%）视为**构建失败级别的回归**
