# 面试追问准备

> 用法：这份文档不是「背答案」，而是**把已经做过的事和已经测出来的数字摆到手边**。
> 每个问题的答法都指向仓库里可核对的东西（命令、文件、基线文档）——
> 说得出「在哪能看到」远比说得出形容词有说服力。
>
> 配套：[index.html](./index.html)（展示页）、
> [../engineering/AI_QUALITY_BASELINE.md](../engineering/AI_QUALITY_BASELINE.md)（全部数字的真源）。

## 回答时的三条原则

1. **先说结论，再给数字，最后讲代价。** 「Agent 化让决策准确率从 83.3% 到 100%，代价是时延 3.6 倍」——
   只讲收益不讲代价，会显得没做过权衡。
2. **不知道就说不知道，并说清怎么验证。** 「这个我没测过，要回答它我需要先建 X 评测」比硬编强。
3. **主动暴露局限。** 面试官迟早会问到；你先说出来，它就从「被抓到的漏洞」变成「你知道边界在哪」。

## 一、定位与价值

**Q1. 为什么做这个项目？**
市面上多数 AI 面试产品是「问几个通用问题 + 给一段泛泛评价」。我的差异点在于：
题目来自**你自己的简历和目标 JD**，评分**必须引用你回答的原文**，报告区分亮点/问题/参考回答/下一步。
跑 `pnpm eval:scoring` 能看到三档答案被拉开 58–63 分——说明它评的不是套话。

**Q2. 它和普通「调 ChatGPT API」有什么区别？**
三件事：结构化契约（schema + 降温重试 + 降级，不接受自由文本直出）、
服务端状态机（九阶段，非法迁移直接拒绝）、以及效果可测量（评测集 + 质量看板）。
大多数 demo 止步于「能跑通」，这个项目能回答「跑得好不好」。

## 二、Agent 相关（最可能被追问）

**Q3. 追问为什么要做成 Agent？**
旧链路是「拼一份固定上下文 → 单次调用 → 出决策」，模型想确认简历细节也无从下手，
追问容易停在「再多说一点」这种泛泛句式。改成 Agent 后，模型可以先检索简历/JD/历史再决策。
对照实验：决策准确率 83.3% → 100%，典型失效场景（回答已充分却仍追问）消失了。

**Q4. 值吗？时延翻了 3.6 倍。**
这是我在文档里明确记下的代价（1.7s → 6.1s）。我的判断是值得：
追问发生在用户答完题之后，6 秒仍在可接受范围；而误追问会直接破坏「被面试」的体验。
如果未来要优化，方向是同轮多工具并行、对「明确进下一题」提前短路、工具结果按会话缓存——
我没有继续加大复杂度，因为收益已经边际递减。

**Q5. 模型乱调用工具、死循环怎么办？**
四层防护，全部与 Agent 解耦：
① 工具白名单由 schema `enum` 强制，未知工具在校验层就被拒；
② `final` 与 `tool_calls` 互斥（同时出现或同时为空都拒绝）；
③ 轮数上限 3，超轮按失败处理并降级为下一题；
④ 最终决策仍过敏感词与后置校验。
集成测试里「达到 2 层追问后即使模型仍要求追问，也被强制推进」在 Agent 化后依然通过。

**Q6. 为什么不用供应商的 function calling？**
三个理由：不依赖供应商能力（DeepSeek/Qwen/GPT 支持程度不一，换模型零成本）；
工具调用与思考在同一份 schema 内，可校验可限速；能复用现有的 `parseWithRetry`。
代价是要自己实现循环，但总共约 270 行（`lib/ai/agent/loop.ts` 142 行 +
`lib/ai/agent/tools.ts` 131 行），且完全可控、可单测（15 条）。

## 三、效果与可靠性

**Q7. 你怎么证明评分是准的？**
三个可复现的数字（跑 `pnpm eval:scoring`）：一致性——重复评分标准差 2.2 分（百分制）；
区分度——好/中/敷衍三档被拉开 58–63 分且顺序 100% 正确；证据合规——42/42 条引用来自回答原文。
**关键设计：不断言绝对分数**，只断言相对顺序。绝对分数会随模型漂移，断言它只会得到一堆反复失效的测试。

**Q8. 模型输出不稳定怎么处理？**
`lib/parsing/run.ts` 统一处理：schema 校验失败 → 降温重试（0.7 → 0.2）→ 仍失败则给可读错误。
特别处理了 `finish_reason === 'length'`（被 max_tokens 截断），
因为截断的 JSON 曾被误报成「模型不会输出 JSON」，排查方向完全错了。

**Q9. 幻觉怎么防？**
两层：prompt 规则（禁止编造经历/数字/技能，不确定的细节必须查工具或写成占位符）
+ 服务端校验（`verifyEvidenceQuotes` 要求每条引用是回答原文的子串，不匹配的直接剔除，
  全部不匹配则视为无效评分并重试）。评测显示 42/42 条引用通过校验。

**Q10. 踩过最坑的技术问题是什么？**
推荐讲这一个：`pdfjs-dist` 被 webpack 打包进 server bundle 后加载即抛错，
导致简历上传路由**整体 500**。单测完全发现不了——只有对每个 API 发真实 HTTP 请求才暴露。
同类还有：连接池必须挂 `globalThis`（Next dev 会把同一模块打进多个 bundle，各建一个连接池，
跑几轮 E2E 就耗尽连接，表现为所有页面空白，看起来像 UI 回归）。
README 里记了 28 条这类问题，每条都有现象、根因、修法。

**Q11. 成本怎么控制？**
`pnpm ai:quality` 给出真实分布：单次调用均值 ¥0.0068，全流程 203 次调用共 ¥1.39。
`plan`（一次生成 8–12 题）P50 近 20 秒、输出 token 最多，是优化优先级最高的一环。

## 四、工程与设计

**Q12. 数据模型怎么设计的？**
12 张表，核心链路 `Question ↔ Answer ↔ Evaluation` 一一可追，
**报告里任一分数都能回溯到具体回答**。追问用 `root_id + depth` 表达父子结构，
使「最多 2 层」可以在 SQL 里直接统计。分数换算必须是服务端纯函数（`lib/ai/scoring.ts`），
不采用模型给的分数，也不散落在模板里算。

**Q13. 合规怎么做的？**
C1–C6 六条红线落到了代码：注册必须同意条款、审计日志、数据可导出可删除、
AI 生成内容明确标识、**不得仅凭 AI 结果做录用判断**。
发给 LLM 的简历做 PII 最小化，日志只记元数据（`ai_call_logs` 不存简历原文）。

**Q14. 免费模式和付费模式怎么兼容？**
产品决策是 V1 全功能免费。做法是**保留支付代码、关闭门禁**而不是删除：
判定集中在 `computeEntitlements()` / `hasReportUnlock()` 两处，
恢复收费只需部署时设 `FREE_MODE=false`，一行业务代码都不用改。
测试默认跑付费模式（`tests/setup.ts` 置 `FREE_MODE=false`），保证门禁断言不被全量放行掩盖。

## 五、短板（建议主动说）

**Q15. 这个项目的最大短板是什么？**
诚实答法：
- **没有真实用户**。尚未内测，完面率这类体验指标无法验证——这是我最想补的。
- **评测样本小**：评分 2 题、决策 6 题，每组 1–2 次。要下「一致性 ±X 分」的结论得跑 `--runs 5`。
- **没有人工标注对齐**：只有相对顺序，没有「人类面试官会打几分」的绝对参照。
- 出题与报告生成仍是评测盲区。
- ~~`prompt_version` 未落库~~ **已修复**：根因是 `LlmRequest` 接口没这个字段，现由各 prompt 模块
  导出 `PROMPT_VERSION`（`parse.jd@1` 这类）并透传到日志，改 prompt 必须递增版本号，有 8 条守卫测试。
  但**新版本号还没有历史数据**，要等积累几轮调用才能做版本对比。

补一句改进计划会加分：扩用例集到 3–5 个岗位方向、做 50 条人工标注算对齐率、
把 plan 与 report 纳入评测。

## 现场可用的三条命令

```bash
pnpm eval:scoring   # 评分质量：一致性 / 区分度 / 证据合规（真实调模型，约 3 分钟）
pnpm eval:agent     # 追问决策：旧链路 vs Agent 对照（约 1 分钟）
pnpm ai:quality     # 调用成功率 / P50-P99 / token 与成本（读真实日志）
```

如果面试官想看代码，优先指这几处：
`lib/ai/agent/loop.ts`（Agent 循环）、
`lib/ai/schemas/evaluation.ts`（评分契约与后置校验）、
`lib/services/handlers/orchestration-service.ts`（状态机与护栏）、
`README.md` 的「已知事项」（28 条踩坑记录）。
