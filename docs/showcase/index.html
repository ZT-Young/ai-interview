它现在是一个 Agent，不是一串 API 调用

追问决策由「思考 → 检索 → 观察 → 再决策」的循环驱动，模型可以自己决定要看什么：

  • search_resume —— 检索候选人真实经历、技能、项目（避免追问时编造细节）
  • search_jd —— 检索岗位硬性要求（判断是否跑题、把话题拉回）
  • recent_answers / asked_questions —— 看历史问答与已问题目，避免重复

护栏全部留在服务端，模型无权绕过：追问层数上限、短回答确定性短路、敏感词降级、轮数上限（3 轮）。工具是纯函数检索，不写库不联网；调用轨迹写入消息 metadata，可回答"它为什么追问这个"。

设计取舍：用结构化 tool_calls（走现有 schema 校验 + 降温重试）而不是供应商的 function calling。 理由是不依赖供应商能力（DeepSeek / Qwen / GPT 支持程度不一）、可校验可限速、轨迹可审计。

三个值得展开的技术点

1. 效果闭环：从「做完了」到「可证明」

此前没有任何东西能回答"它评得准吗"。我建了评测集与质量看板（pnpm eval:scoring / pnpm ai:quality / pnpm eval:agent）。

关键设计：不断言绝对分数。绝对分数随模型和 prompt 漂移，断言它只会得到一堆反复失效的测试；断言相对顺序（好 > 中 > 敷衍）才是稳定判据。同理，全部断言都可自动判定，不依赖人工逐条标注。

评测第一遍就抓到一个真 bug：evidence_quotes 的 schema 强制 min(1)， 但未作答时根本没有原文可引用 → 空回答的评分 100% 失败。单测完全没发现（所有单测用的都是非空回答）。 修法是把业务规则从 schema 上移到服务层。修完成功率 85.7% → 100%。

2. Agent 与护栏解耦

模型可以自主检索，但追问层数、短回答短路、敏感词降级全在服务端判定。集成测试里那条 「达到 2 层后即使模型仍要求追问，也被强制推进下一题」在 Agent 化后依然通过—— 自主性给了模型，边界仍然握在代码手里。

3. 踩坑驱动的实现细节

  • pdfjs-dist 被 webpack 打包会导致上传路由整体 500 —— 单测发现不了，只有真实 HTTP 请求才暴露
  • 数据库连接池必须挂 globalThis：Next dev 会把同一模块打进多个 bundle，各建一个连接池，跑几轮 E2E 就耗尽连接
  • 重复提交同一题会撞唯一约束 → 曾兜底成 500，改为幂等返回当前进度
  • 依赖不可用时返回 503 而不是 500：错误性质不同，用户该做的事也不同

仓库 README 记录了 28 条这类问题，每条都写了现象、根因与修法。

已知局限

  • 评测样本小：评分 2 题 × 每档 2 次；决策 6 题 × 1 次。标准差在小样本上不稳定，要下强结论需 --runs 5
  • 没有人工标注：只有相对顺序，没有"人类面试官会打几分"的绝对对齐
  • 只覆盖评分与追问：出题（plan）与报告（report）仍是评测盲区
  • 没有真实用户数据：尚未内测，完面率等体验指标无法验证
  • 语音面试入口已开放，但 ASR 供应商未接入（返回 503 而非伪造转写）
  • prompt 版本刚接上，还没有历史数据：此前 prompt_version 从未落库（接口没这个字段）， 已修复并加了守卫测试；但新版本号要等积累几轮调用才有对比价值
